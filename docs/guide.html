Developer guide

Custom Design System

A brand-agnostic, white-label UI kit for building consistent, accessible SaaS interfaces. Fork the repo, run one command, and Claude Code knows your project's exact brand, style, and rules — automatically.

12 brand hues 5 style presets 2 themes 50+ components No build step
How it works in one sentence. Three HTML attributes control the entire look — data-theme, data-brand, data-style — and every component reflows instantly with no rebuild.

Three-step flow

1
Fork and clone

Fork this repo on GitHub, then clone your fork locally. This is your project's copy — you can change anything without affecting the upstream.

$ git clone git@github.com:your-org/Custom-Design-system.git my-project
$ cd my-project
2
Run the setup wizard

One command. Asks 6 questions, writes project.config.json, updates CLAUDE.md with binding rules for Claude Code, and generates a pre-configured index.html starter.

$ pnpm setup
3
Open Claude Code

Claude Code reads CLAUDE.md automatically on every session. Your setup choices are binding rules — Claude uses the right brand, style, and components without you having to repeat them.

$ claude

Working with AI

Claude Code

Claude Code reads CLAUDE.md at the start of every session. After running pnpm setup, that file contains your project's brand, style, and rules — Claude follows them without you repeating them.

How it works

1
CLAUDE.md is the contract

The ## Project Config section contains your choices as binding rules. Claude sees: "this project uses brand=indigo, style=enterprise, default size=sm. Only use components from src/whitelabel/."

2
Describe what to build, not how to style it

You provide the product requirements — "a user management page with a sidebar, searchable table, and invite button." Claude handles component selection, token usage, and accessibility automatically.

3
Point to the showcase when needed

If Claude is unsure about a component, say: "open Whitelabel UI Kit.html, find the DataTable spec card, and use that exact API." Every spec card has a working JSX example.

Corrections when Claude drifts

Claude used a raw hex color
Replace with the semantic token. Rule 2 in CLAUDE.md: consume the semantic layer, never the scale.
Claude invented a component not in src/whitelabel/
Check the showcase. Every component exists there. If you can't find it, describe the layout using primitives (Card, Button, etc.).
Claude used the wrong brand or style
The <html> element must carry the data-brand and data-style from your CLAUDE.md Project Config section.
Claude added a decorative second color
One brand, one accent. Any second color must come from the status taxonomy: success / warning / danger / info.

Non-negotiables

10 rules

These rules apply to every screen, every component, and every piece of custom CSS. They're written into CLAUDE.md so Claude Code follows them automatically.

1
Never inline raw values
No hex colors, no raw px for spacing/radius, no raw ms durations. Every visual value must come from a token.
✓ color: var(--fg-default); padding: var(--space-4); ✗ color: #1a1a1a; padding: 16px;
2
Consume the semantic layer, not the scale
Use semantic aliases. Never reference primitive scales directly — only tokens.css itself should do that.
✓ var(--fg-muted) var(--bg-brand) var(--border-subtle) ✗ var(--neutral-500) var(--indigo-600) var(--neutral-200)
3
One brand, one accent
Never introduce a second hue alongside brand. A second color must come from the closed status set.
✓ success / warning / danger / info ✗ A second brand hue added for visual decoration
4
Variant maps to intent
One primary action per surface. Danger always confirms. Ghost for toolbars and icon rows.
✓ variant="primary" (submit/save) variant="danger" (destructive + confirm) ✗ Two primary buttons on the same surface
5
Match size to context
xs/sm for tables and toolbars. md for forms and page actions (default). lg for landing CTAs and empty states.
✓ size="sm" in table rows size="lg" in empty states ✗ size="lg" for every button regardless of context
6
Status taxonomy is closed
success, warning, danger, info — never invent a fifth. Badge, Alert, and Progress all share this exact set.
✓ variant="success" variant="warning" variant="danger" variant="info" ✗ variant="purple" variant="neutral-special"
7
Light and dark are equal citizens
Test every screen in both themes. Components get dark mode for free via tokens. Any custom CSS you write must too.
✓ color: var(--fg-default); /* works in both themes */ ✗ color: #000; /* invisible in dark mode */
8
Accessibility floor
AA contrast (4.5:1) on text. Touch targets ≥ 32px. Icon-only buttons require ariaLabel. Status conveyed by color must also carry an icon or text.
✓ <IconButton ariaLabel="Delete item" icon="trash" /> ✗ <IconButton icon="trash" /> {/* screen readers can't describe this */}
9
Form fields need labels
Always set label and either placeholder or hint. Errors use error + hint together. Required fields get required prop.
✓ <Input label="Email" placeholder="you@example.com" required /> ✗ <input type="email" /> {/* unlabelled, inaccessible */}
10
Respect the spacing rhythm
The grid is 4-point. Most layouts use --space-3/5/7/8 (8/16/24/32). Never break the grid with arbitrary values.
✓ gap: var(--space-4); padding: var(--space-5); ✗ gap: 13px; padding: 18px;
